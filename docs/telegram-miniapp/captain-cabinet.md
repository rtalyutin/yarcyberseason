**Актуальная поправка, 09.10.2026, 08:19 МСК:** «После окончания матча удаляем».
Вся переписка хранится в текущем S3 до официального завершения матча; чтение
ничего не удаляет. Сообщения должны переживать перезапуск и вход через неделю.
После завершения переписка удаляется целиком, без архива. Это заменяет прежние
варианты с 30-минутным RAM-буфером и удалением после прочтения.

Организатор заранее вводит Telegram @username капитанов напротив команд на
`/org`; `/orgs` остаётся совместимым адресом. После проверенного Telegram-входа
появляется кнопка кабинета. В карточке матча — приватный чат двух капитанов,
под ним дата/время МСК и кнопка «Время согласовано». Каждый подтверждает одну
версию времени; изменение сбрасывает согласие. Только два подтверждения дают
согласованное время, сохранённое сервисом в S3 и видимое на `/org`.
Сообщения в Telegram не отправляются. Заявленный капитаном результат остаётся
заявкой организатору и не меняет официальный счёт, сетку или MVP.

## API v3

Все private ответы `no-store`. Tournament scope: `dota2-autumn-2026`.
Первый проверенный вход закрепляет числовой Telegram user id за записью
капитана; смена username не передаёт права другому аккаунту. Смена/удаление
назначения организатором отзывает прежнее право и его неподтверждённое согласие.

`POST /api/captain` принимает `{initData, action, ...input}`. `initData`
проверяется сервером по Telegram Ed25519 и id бота, включая срок действия.
Serverless endpoint `captain` передаёт запрос через `sdk.fetch`; сервис повторно
проверяет подпись. Клиент обращается через `Telegram.WebApp.Serverless.call`.
В DTO нет Telegram id других пользователей или полного реестра капитанов.

Действия:

- `access` → `{authorized, team: {id,name}|null, matches: Match[]}`.
- `match` + `matchId` → `MatchDetail`.
- `message` + `matchId, requestId, expectedChatEpoch, text` → `MatchDetail`.
- `agree` + `matchId, requestId, expectedScheduleVersion, startsAt` → `MatchDetail`.
- `result` + `matchId, requestId, score: [number,number], comment` → `MatchDetail`.

`Match`: `{id, team1:{id,name}, team2:{id,name}, round, bestOf, status,
scheduledAt, window:{start,end}|null, broadcastUrl:null|string, note:string}`.
`MatchDetail`: `{match:Match, viewerTeamId, chatEpoch, chatClosed:boolean,
messages:[{id,teamId,text,createdAt}],
scheduleVersion:number, proposal:null|{startsAt,confirmedTeamIds:string[]},
agreed:null|{startsAt,agreedAt}, resultClaims:[{id,teamId,score,comment,createdAt}]}`.
Время ISO с offset, вход UI конвертируется из МСК явно, независимо от пояса ОС.
`agreed` хранит последнее завершённое согласование, пока новое ожидает вторую
сторону. История назначений, согласований и заявок, их fingerprints и receipts
сохраняются. Сообщения и их данные идемпотентности тоже сохраняются, но только
до завершения матча. Повтор того же запроса не создаёт дубль; прежний requestId
с другим содержимым отклоняется. Клиент создаёт новый UUID для каждого действия.
`chatEpoch` сохраняется после перезапуска; смена назначения капитана меняет
epoch, не удаляя переписку. Старый `expectedChatEpoch` даёт `chat_reset`:
клиент снимает повтор команды, сохраняет черновик и перечитывает состояние.
Отправить черновик в новый чат можно только отдельным действием пользователя.
После официального завершения `chatClosed:true`, `messages:[]`; любые отправки,
включая повтор прежнего requestId, получают `match_closed`. Закрытие проверяется
до идемпотентности. UI убирает ожидающий повтор и блокирует отправку; отдельная
заявка о результате остаётся доступной. Чтение переписки не меняет её состояние.

`GET /api/orgs/captains` после существующего bearer login →
`{revision,teams:[{id,name}],bindings:[{teamId,username,linked:boolean}],
matches:MatchDetail[]}`. `POST` туда же:
`{requestId,expectedRevision,teamId,username}`; `username:null` отзывает доступ.
Ответ — тот же DTO, но `messages:[]`, `chatEpoch:null`: переписка доступна только
двум капитанам, не организатору и не на публичных страницах.

Коды: `unauthorized`, `forbidden`, `not_found`, `invalid_request`,
`conflict`, `idempotency_conflict`, `chat_reset`, `captain_not_configured`,
`window_unavailable`, `outside_window`, `too_late`, `match_closed`, `storage_unavailable`,
`capacity_reached`, `too_many_requests`. Conflict требует перечитать состояние;
сетевой timeout не доказывает неуспех — читать состояние и повторять тот же id.

## Хранение и границы выпуска

Одна зашифрованная запись состояния турнира в **существующем** Timeweb S3 bucket
`e9dc5ea4-6dc9267d-85ca-4ae9-a41f-2895e9542a04`, обновляемая по ETag
`If-Match`/`If-None-Match`. В ней реестр, согласования, заявки с их служебной
историей и переписка незавершённых матчей. Официальный
`results/dota2-autumn-2026.json` не изменяется. Нового bucket или сервиса нет.
Сообщения не копируются в постоянные файлы, логи, public DTO или browser storage.

У переписки нет TTL и вытеснения по правилу «последние 100». Нехватка ёмкости
отклоняет новую запись без удаления старой переписки. Чтение через неделю и
перезапуск backend сохраняют сообщения незавершённого матча. Назначения
проверяются при каждом запросе; старый капитан теряет доступ, новый представитель
команды получает существующий разговор. Браузер перечитывает его каждые 5 секунд.
Пары матчей загружаются один раз при старте backend; обновления результатов
не меняют участников. Изменение пар требует отдельной проверки данных;
динамическая подмена каталога в работающем процессе не поддерживается.

Очистка выполняется существующим Node backend при запуске и далее раз в минуту,
без перекрывающихся запусков, независимо от открытых клиентов. Основание —
валидированное официальное завершение (`completed`/`resultConfirmed`), а не
запланированное время, прочтение сообщения или заявление капитана. Ошибка чтения
источника не означает завершение; сервис повторит проверку. Это периодическая
проверка публикации результата, не обещание мгновенного определения конца игры.

Одна CAS-операция устанавливает необратимый `chatClosed` и удаляет сообщения,
их fingerprints, receipts и события переписки данного матча. Минимальный
receipt самой очистки без текста нужен для проверки неизвестного исхода PUT.
Время, подтверждения, реестр и отдельные заявки сохраняются. Гонка с отправкой
не воскрешает чат: поздний CAS повторно проверяет закрытие. Откат результата
или перезапуск не снимают сохранённый признак закрытия.

Код очищает текущее состояние S3. До выпуска отдельно проверить версии объектов,
резервные копии и Object Lock для этого key: сохранённые старые копии могут
содержать ciphertext прежней переписки. Физическое удаление всех копий не
подтверждено локальными тестами. Политику общих публичных данных не менять.

Приватные реестр, заявки и переписка защищены AES-256-GCM с серверным ключом, новым
случайным 12-байтовым nonce на каждую запись и 16-байтовым tag. AAD связывает
версию формата, bucket, key и турнир. Шифрование не зависит от публичности
GET в существующем bucket; права записи должны оставаться серверными.
`ACL:private` и `Cache-Control:no-store` — дополнительные меры.
Неподтверждённое окно блокирует запись времени, но не чтение и чат.

Состояние хранится в `captains/dota2-autumn-2026.json`, схема v3 внутри
версионированного зашифрованного envelope. Старый незашифрованный формат
не принимается; предыдущая реализация не публиковалась.
Пустой объект создаётся условно при первой записи, без SQL-миграции. Совместимый
JSON проверяется после проверки tag/расшифровки и перед записью; повреждённое
состояние или неверный ключ не обнуляют данные. Без ключа сервис закрыт.
Ключ нужен для восстановления: его замена без перешифрования делает прежние
данные недоступными. Лимит 8 MiB относится к расшифрованному состоянию;
envelope ограничен отдельно с учётом Base64. Превышение возвращает
`capacity_reached` без удаления истории. Команды сохраняют fingerprints/receipts
в той же версии; служебные записи сообщений имеют matchId для точной очистки;
после CAS-конфликта до 8 попыток с повторной проверкой прав. TTL auth — 1 час,
потом пользователь заново открывает Mini App. Подпись другой среды/бота,
дубли полей и подмена user отвергаются. Оба подтверждения нужны не позднее чем
за 2 часа до выбранного начала, включая ровно двухчасовую границу.

Подготовка локального Serverless-кандидата после выбора target:
`node scripts/prepare-captain-serverless.mjs` затем `npm run build`.
Скрипт записывает только публичный URL в `tgcloud/lib/config.js`.
Корневой `tgcloud.json` ссылается на `dist/client` внутри проекта; путь открытия Mini App —
`/tg`, приватный кабинет — `/tg/tournament?section=captain`.
Пустой URL по умолчанию означает отказ, не скрытый альтернативный backend.
Endpoint не импортирует Node/npm и не вызывает Bot API.

CLI `@tgcloud/cli` 0.2.0 поддерживает адресный push: из корня репозитория
`tgcloud push tgcloud/endpoints/captain.js tgcloud/lib/captain-relay.js tgcloud/lib/config.js`.

бота через штатный login/fetch и сверить revision; force не использовать.

объекта в текущем bucket, серверные права записи и поддержку S3 условных записей
в разрешённой среде. Политику публичных результатов не менять ради кабинета.
